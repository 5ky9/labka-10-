# Agromarket React Frontend

Проект клиентской части веб-приложения «АгроМаркет».

## Тестирование
- `npm test` — компонентные тесты (Vitest + Testing Library), моки fetch
- `npm run coverage` — покрытие кода тестами
- `npm run e2e:prod` — E2E (Playwright) на продакшене; в CI — ежедневно и по кнопке

## Лабораторная 10 — ответы

- **Сколько компонентных тестов и какие компоненты покрыты:** 
  12 компонентных тестов. Покрыты компоненты: `ProductCard`, `LoginForm`, `Catalog`, `OrderForm`, `smoke`.

- **Какие реальные дефекты нашли тесты:**
  1. В `LoginForm` у тэгов `<input>` отсутствовали связанные атрибуты `<label htmlFor="...">`, из-за чего экранные дикторы не связывали подписи с полями.
  2. В `Catalog` отсутствовало обработанное состояние загрузки (`loading`), из-за чего интерфейс был пустым во время ожидания ответа от сервера на "холодном старте" Render.

- **Покрытие:** 
  Общее покрытие линий (% Lines): **82%**. Хуже всего покрыты утилиты работы с сетью и некорректными статусами ошибок, так как они обрабатывают крайние редкие случаи.

- **Время выполнения:** 
  Компонентные тесты: **1.8 с**, E2E-тесты на продакшене: **24 с**. E2E-тесты медленнее примерно в **13 раз**.

- **Что увидели в trace упавшего теста:** 
  При открытии `npx playwright show-trace` видны пошаговая раскадровка (snapshots), состояние DOM-дерева на каждом действии, логи консоли браузера и тайминги сетевых запросов fetch.

- **Почему E2E не запускаем на каждый PR:** 
  E2E-тесты проверяют развернутый продакшен/стейджинг, а не код из локального PR. Запуск E2E на каждый PR затягивает сборку и может создавать лишнюю нагрузку и тестовый мусор в базе данных.

- **Сколько e2e-пользователей в базе и чем это плохо:** 
  В базе Neon накапливаются пользователи вид `e2e+17...@agromarket.test`. Это засоряет таблицы пользователей и искажает аналитику.

- **Использовал(а) ли ИИ и для чего:** 
  ИИ использовался для подбора конфигурации Vitest с jsdom и написания базовых сценариев Playwright.
